# Your roadmaps — Implementation Plan (part 1 of 4: data, routes, the list and the loader)

**Intent:** docs/roadmaps/intent.md (criteria 1–11 here, with 33 and 35 as far as part 1 reaches them; parts 2–4 get their own plans when their turn comes). **Reference:** docs/roadmaps/reference/ — `logic/roadmaps.js` and `logic/roadmaps-template.html` (the list, the dialogs, the loader's steps and timing `LT`), `canvas/roadmaps.css` (the look: sizes, the card, the dialogs, the loader's `rm-*` rules) and `canvas/road.css` lines 687–717 (`rb-load*`, the loader's steps). Canvas: the Roadmaps page (RMDesk, RMPhone, RM1920, RMFirstDesk/Phone, RMMenuDesk, RMNewDesk/Phone/1920, RMReadyDesk, RMFirstLoadDesk/Phone/1920, RMFirstSlowDesk, RMFirstErrorDesk, RMLoadDesk).
**Goal:** a student's answers and board live on roadmaps she can list, open, rename and delete; onboarding ends on the loader and lands on `/roadmaps`; the board is `/roadmaps/[id]`.
**Approach:** a new feature `src/features/roadmaps` with the stored model (one `roadmap` table), its server module and actions, the list page and the loader; the opening feature's profile module keeps its signatures but reads and writes the roadmap she is answering, so every onboarding screen stays as it is; the road feature's board moves under `/roadmaps/[id]` and saves its choices per roadmap. A migration moves each existing student's answers into her first roadmap.
**Test layers:** unit plus integration. Criteria 1, 2, 4, 7 and 9 cross the database (a roadmap's full copy of answers, soft delete and Undo, the last-opened order, the one unfinished roadmap per student, the first roadmap created on finishing), so the roadmap server module gets database tests run by path with `DB_TESTS=1 DATABASE_URL=… bun test src/features/roadmaps/server/roadmaps.test.ts` (as src/features/opening/server/profile.test.ts does; never `bun run test:db`). Everything else is unit (bun test, happy-dom): the landing rule, the loader's step model, the actions (profile module mocked as src/features/opening/actions.test.ts does), the list's menu and dialogs, the board's persisted choices. The routing (criterion 3 and the lock) is checked by the standing e2e/routes.e2e.ts, which the repo already runs against the dev server; the look (criteria 5, 6, 11's layout) is the smoke test and screenshots against the RM* boards. Access: every read and write takes the user id from the session (`asStudent`), and the database tests prove that a roadmap of another student is not returned, renamed or deleted.
**Constraints (CLAUDE.md):**
- `bun install` (Bun only; npm/pnpm/yarn are refused)
- Never commit or push without explicit approval. Squash micro-commits into one semantic commit. Never add co-author text to commit messages.
- Conventional Commits (`type(scope?): description`), enforced by .husky/commit-msg.
- Never start a dev server for the user; they run it.
- `bun run test:db` — **wipes the development database** (never run it; database tests run by path with `DB_TESTS=1`)
- Access rules live in one pure module, src/shared/lib/auth/access.ts; pages and actions call it, the proxy only checks the cookie. New signed-in pages go under src/app/(app) and into APP_PATHS and the proxy matcher together.
- Every redirect is answered before anything is painted, and in one hop: student and admin pages have no `loading.tsx`.
- Server actions return `ActionResult` (src/shared/types/action-result.ts) and never throw.
- Tailwind 4 is CSS-first (src/app/globals.css): semantic tokens only, no @apply, OKLCH colours, rem not px (hairlines 1px; icons `size-icon-sm` / `size-icon` / `size-icon-lg`). Dark mode follows `<html data-theme>`.
- Sizes are fluid through the design system's roles: type `text-display`, `text-h1` to `text-h4`, `text-lead`, `text-caption`, `text-overline`; spacing `px-gutter`, `py-section`, `gap-section`, `gap-stack`. Never a size per breakpoint.
- Layout responds to the page's own width (container queries on an `@container` root): `@max-xl:` below 36rem, stacked between 36 and 64rem, `@5xl:` from 64rem. Grids inside content size themselves (`repeat(auto-fit, minmax(…, 1fr))`); never an arbitrary `@max-[…]`, `@min-[…]` or `max-w-[…]`.
- The active design system is Industry: read src/design-systems/industry/DESIGN.md before any UI work.
- Read node_modules/next/dist/docs before writing Next.js code (AGENTS.md).
- Test the brain, not the beauty: unit tests pin logic, hooks, actions and components with behaviour (test-first); pages, layouts, styles and presentational pieces get none.
- Every action is the shared `Button` (variants `strong`, `outline`, `text`, `square`); notes are `Note`; dialogs are the shared shadcn `Dialog` (src/shared/components/ui/dialog.tsx), sheets the shared `Sheet`; behaviour lives in components, never per page.
