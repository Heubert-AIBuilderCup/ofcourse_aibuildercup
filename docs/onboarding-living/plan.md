# Step 03, Where and how you'd live: one question per screen — Implementation Plan

**Intent:** docs/onboarding-living/intent.md
**Goal:** Step 03 asks one question per screen at `/onboarding/living/<question>` on the onboarding shell, reusing step 02's `QuestionScreen`, with "Who, and where?" as a form whose every part may be blank.
**Approach:** Step 02's per-step model (`QUESTION_STEPS` in `onboarding.ts`) gains step 3. The person screen is a step question with the pseudo key `'person'` (not a stored answer: it reads and writes the stored `relative`). The person's schema loosens (any part null); one helper names the contact for both the screen's line and the futures' distance line. `QuestionScreen` learns step 3: the person form instead of cards on `'person'`, and the step's own notes.
**Test layers:** Unit only (`bun test <files>` per task; `bun run test:run` once at the end by the controller). The access path is unchanged (new pages under `src/app/(app)` behind `requireStudent`, as step 02's). The looser person schema is pinned in the action's unit tests (no DB test: the column is jsonb and the write path `saveRelative` is unchanged). Criterion 14 is a screenshot check by the controller. No e2e (CLAUDE.md: only when asked).
**Constraints:** CLAUDE.md in full; in short: Bun only; server actions return `ActionResult` and never throw; Tailwind 4 semantic tokens, container-query variants (`@max-xl:`, `@5xl:`), type/spacing roles, `size-icon*` for icons, no arbitrary values; student URLs as slugs, keys never in a URL; "test the brain, not the beauty" (no tests for pages or styles); never `bun run test:db`, `bun run db:reset`, `bun run test:e2e`, or a dev server; read `src/design-systems/industry/DESIGN.md` before UI work and `node_modules/next/dist/docs` before Next.js code; commit after each task with Conventional Commits, no co-author line.
